# AGENTS.md

Personal NixOS flake in `/etc/nixos`, single user (`xjle`), two hosts. The flake uses the
dendritic pattern: `flake.nix` is a thin entrypoint, `import-tree` auto-imports every
`.nix` file under `modules/`, and each non-entry file is a flake-parts module exporting
`flake.modules.nixos.*` and/or `flake.modules.homeManager.*`.

| Flake attr | `networking.hostName`   | Hardware     |
| ---------- | ----------------------- | ------------ |
| `desktop`  | `nixos` (NOT `desktop`) | AMD + NVIDIA |
| `thinkpad` | `thinkpad`              | Intel        |

## Commands

- Rebuild/activate: `sudo nixos-rebuild switch --flake /etc/nixos#desktop` (or `#thinkpad`).
  The user runs this themselves (fish alias `nrs` = `...#desktop`; thinkpad's = `...#thinkpad`).
- Validate without activating: `sudo nixos-rebuild build --flake /etc/nixos#desktop`
- Full config eval (catches module errors without building):
  `nix eval --raw /etc/nixos#nixosConfigurations.desktop.config.system.build.toplevel.drvPath`
- Fast eval: `nix eval --raw /etc/nixos#nixosConfigurations.desktop.config.networking.hostName`.
  `--raw` only works for strings; use `--json` for booleans.
- Update inputs: edit `.tack/pins.toml`, then run `tack update` (rewrites `.tack/pins.lock.json`).
  CLI also has `tack add` / `tack rm` / `tack alias`. `nix flake update` is a no-op here —
  `flake.lock` is an empty stub.
- Agent `sudo` is blocked by permission rules. Don't start the long rebuild — hand `switch`/activation to the user.
- No CI, tests, lint, or formatter config. `nixfmt` and the `home-manager` CLI are NOT
  installed; use `nix run nixpkgs#nixfmt-rfc-style -- <file>` if formatting is needed.
  Home-manager is only used as a NixOS module, so all changes go through `nixos-rebuild`.

## Dendritic rules

- New files are invisible to `nixos-rebuild --flake` until `git add`ed.
- `import-tree` only scans `modules/`; underscore-prefixed dirs are skipped.
- Config must live inside `flake.modules.nixos.<name>` or
  `flake.modules.homeManager.<name>`. Bare top-level NixOS/HM options are not applied.
- Loading a file is not enabling it: a host only gets an aspect if an aggregator or host
  module lists its name (e.g. `foo` in `modules/nixos/common.nix` or `desktop.nix`).
- Filename and aspect name may differ (`olama.nix` exports `ollama`); aggregators use the
  aspect name.
- One file can export several aspects, and its directory does not decide the target —
  aggregators import by aspect name. `modules/nixos/desktop/noctalia.nix` exports `noctalia`,
  which `common.nix` imports on both hosts; `modules/nixos/docker.nix` exports both `docker`
  and `docker-nvidia`.
- Outer wrappers use `{ inputs, config, ... }` when they need flake inputs or other
  aspects. There are no `specialArgs`; `inputs` is captured lexically.

## Layout

- `flake.nix` — thin entrypoint; inputs come from `import ./.tack`, then
  `flake-parts.lib.mkFlake { inherit inputs; } (inputs.import-tree ./modules)`.
- `.tack/` — tack input manager: `pins.toml` (hand-edited), `pins.lock.json` (generated),
  `default.nix` (tack-managed resolver; do not hand-edit).
- `modules/flake-parts.nix` — sets `systems` and imports
  `inputs.flake-parts.flakeModules.modules` (required for `flake.modules.*` merging).
- `modules/hosts/*.nix` — `flake.nixosConfigurations.<host>`; each installs one named
  aspect (`config.flake.modules.nixos.desktop` / `.thinkpad`).
- `modules/nixos/` — NixOS aspects. `common.nix`, `desktop.nix`, and `thinkpad.nix` are
  aggregators; `settings.nix` holds the main shared system config, `home-manager.nix`
  holds the HM wiring.
- `modules/nixos/desktop/` — NixOS aspects (`nvidia`, `games`, `tablet`, `obs`, `ollama`,
  `cachykernel`, `noctalia`, `umbriel`, `wallpaperengine`). `docker-nvidia` and `lamp` are
  desktop-only too but live directly in `modules/nixos/`. `noctalia`/`umbriel` here only add
  Cachix caches and are imported by `common.nix` on both hosts despite the directory name.
- `modules/nixos/hardware-*.nix` — point at the untouched `devices/*.nix` files.
- `modules/home/` — home-manager aspects. `base.nix`, `desktop.nix`, and `thinkpad.nix`
  are aggregators; `user.nix` holds the old `home.nix` basics.
- `modules/home/config/` — files installed via `xdg.configFile` (store-backed); edits only
  reach `~/.config` after a rebuild.
- `devices/*.nix` — generated by `nixos-generate-config`; do not edit.

## Inputs (tack)

- `flake.nix` gets inputs from `import ./.tack { overrides = args.tackOverrides or { }; }`;
  `flake.lock` is an empty stub, so `nix flake update` changes nothing.
- `.tack/default.nix` is tack-managed — don't hand-edit it. `pins.toml` declares
  `[inputs.<name>]` (`url`, `type` = flake/fetch/fixed, `follows`, `dir`, ...);
  `pins.lock.json` is tack-generated and is what Nix actually reads. Commit both.
- `[all_follow]` in `pins.toml` maps an input name to the top-level pin it follows;
  `exclude_follow` opts out, and `flake:` / `tack:` prefixes restrict a follow to one side.
  Check `pins.toml` rather than assuming every input follows nixpkgs.
- nixpkgs is pinned to `github:nixos/nixpkgs/nixos-unstable` in `pins.toml`.
- `system.stateVersion` is `"26.11"` for NixOS and home-manager; do not downgrade.

## Device branching

- No `hw_file` / `device` specialArgs. Host differences are named aspects:
  `flake.modules.nixos.desktop` / `.thinkpad` and
  `flake.modules.homeManager.desktop` / `.thinkpad`.
- Hostnames are set in `modules/nixos/{desktop,thinkpad}.nix`; kernels too: desktop uses
  `linuxPackages_zen`, then `desktop/cachykernel.nix` `lib.mkForce`s the CachyOS zen4
  kernel; thinkpad uses `linuxPackages_xanmod`.
- Thinkpad gets foot/fuzzel/firefox and its own niri/wlogout variants; desktop gets
  kitty/rofi/opencode/helium/games/wine.
- `modules/home/niri.nix` and `modules/home/wlogout.nix` generate both device variants
  from a shared `let` binding.

## Wayland stacks

- Active: **Niri + Noctalia** and **Umbriel** — `programs.niri.enable` and
  `programs.umbriel.enable` are true in shared `modules/nixos/programs.nix` on both hosts;
  desktop also imports `inputs.umbriel.nixosModules.default`. Niri config is per-device:
  `modules/home/niri.nix` exposes `niri-desktop` / `niri-thinkpad`, writing
  `~/.config/niri/config.kdl`; `modules/home/config/niri.kdl` spawns `noctalia` and
  `skwd-walld`.
- **Umbriel HM is per-device, not shared `base`**: `modules/home/umbriel.nix` exports
  `umbriel-desktop` / `umbriel-thinkpad`, imported by the matching HM aggregator. It sets
  `programs.umbriel.settings` from `./config/umbriel/config.toml` and adds a drop-in via
  `xdg.configFile."umbriel/config.d/90-user-extra.toml"`; the numbered `10-80` files and
  `noctalia.toml` stay runtime-managed. Edits here are store-backed and need a rebuild.
- **Mango + DankMaterialShell are disabled but still wired**: `programs.mango.enable =
false` in `programs.nix` (the mangowm NixOS module is still imported by desktop), and
  `modules/home/dms.nix` gates DMS on mango being enabled. Re-enable by flipping that
  flag; the mango HM aspect still installs `~/.config/mango/`.
- Desktop-only `inir` HM aspect rides the Umbriel session: upstream hardcodes
  `niri.service`, so `modules/home/inir.nix` mkForces its systemd unit onto
  `umbriel.service`, and mkForces iNiR's quickshell build so `bin/qs` doesn't collide
  with DMS's.
- Default session is Plasma 6 via `lib.mkForce "plasma"` (`modules/nixos/services.nix`);
  hyprland is off.

## Gotchas

- `programs.qylock` is enabled in `settings.nix` for both hosts;
  `inputs.qylock.nixosModules.default` is imported by `common.nix`.
- `devices/thinkpad.nix` generates an invalid empty swap device;
  `modules/nixos/thinkpad.nix` forces `swapDevices = [ ]`.
- Bootloader is limine (`modules/nixos/boot.nix`), not systemd-boot/grub. It hardcodes a
  Windows 11 EFI entry, adds `amdgpu` to initrd on both hosts, and uses plymouth theme
  `mac-style`. Desktop-only `amdgpu.dcdebugmask` lives in `modules/nixos/desktop.nix`.
- `modules/home/opencode.nix` is desktop-only: it installs
  `modules/home/config/opencode/opencode.jsonc` via `xdg.configFile.source` (store-backed,
  needs a rebuild), adds `uv`, the impeccable skill/command and three Matt Pocock skills.
  The impeccable engine is a pinned `fetchurl` (engine-v0.1.27) — bump it and the
  `impeccable` pin in `.tack/pins.toml` together. The numtide substituter is in
  `modules/nixos/desktop/olama.nix`; `opencode2` comes from `modules/home/desktop.nix` via
  `llm-agents`; the config uses the V2 `plugins` key.
- nixvim is wired in two places: the NixOS module is imported only by thinkpad
  (`modules/nixos/thinkpad.nix`), while the HM module is shared to all users via
  `home-manager.sharedModules` (`modules/nixos/home-manager.nix`).
- `.git/objects/e6.root` is a root-owned leftover; git ignores it. If `git add` fails on
  a root-owned `.git/objects/*` dir, the user must chown it.
- Binary caches: always use `nix.settings.extra-substituters` /
  `extra-trusted-public-keys`. Plain `substituters` / `trusted-public-keys` replace NixOS
  defaults and drop `https://cache.nixos.org`.
- SSH is key-only on both hosts (`PasswordAuthentication` and
  `KbdInteractiveAuthentication` false in `services.nix`); adding a client means appending
  its public key to `modules/nixos/users.nix`.
- LAMP is desktop-only (`modules/nixos/lamp.nix`): Apache + PHP-FPM, MariaDB on 3306 and a
  hand-rolled MySQL 8.4 instance `mysql8` on 3307. That unit must be `Type = "simple"`
  (mysql84 has no notify support) and its postStart creates `xjle@localhost`; the php-fpm
  pool must set `pm.min_spare_servers` / `pm.max_spare_servers` or it exits 78.
- GTK2: force an overwrite with `gtk.gtk2.force = true` in `modules/home/gtk-qt.nix`.
  `home.file.".gtkrc-2.0".force` gives a conflicting-target eval error because home-manager
  keys that file by its absolute configLocation.
- Docker has two aspects in `modules/nixos/docker.nix`: `docker` (in `common`, both hosts;
  daemon has `enableOnBoot = false`) and `docker-nvidia` (desktop only — the NVIDIA
  container toolkit asserts NVIDIA drivers are present).

## Coding guidelines (Karpathy)

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
